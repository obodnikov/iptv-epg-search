# AI-coding setup

Produce a consistent, project-specific set of AI-coding docs:

- **CLAUDE.md** — project-global behavior + the index of rule files + tooling commands.
- **ARCHITECTURE.md** — structure, components, data flow, stability zones, rule precedence.
- **AI_<COMPONENT>.md** — one coding-rule file per architectural component, tagged with its stack.
- **.agents/skills/review-fix-loop/** — an autonomous review loop with stack-aware verify commands,
  linked into `.claude/skills/` for Claude Code (optional).
- **.claude/settings.json `ask` list + .pi/bash-restrictions.json** — which commands Claude Code and
  pi must ask about before running (optional; only when the user asks for it).

The hard part is **multiple stacks in one project**. The solution: split the `AI_*.md` files by
**architectural component/boundary, each tagged with its stack** — see
[references/house-style.md](references/house-style.md). One Python pipeline gets several Python
`AI_*.md` files by layer; a React+Python+Docker app gets `AI_FRONTEND.md` + `AI_BACKEND.md` +
`AI_INFRA.md`. CLAUDE.md and ARCHITECTURE.md §8 index whichever set you produce.

Bundled resources (paths relative to this skill directory):
- `scripts/detect_stacks.py` — repo scanner (stdlib only; run with `python3`).
- `scripts/pi_restrictions.py` — compares the pi reference with the global pi file and builds a split
  project file (stdlib only; Step 7).
- `references/house-style.md` — conventions + per-placeholder fill rules. **Read before generating.**
- `references/stack-rules.md` — per-stack rule catalog for the `AI_*.md` files.
- `references/architecture-guide.md` — how to fill ARCHITECTURE.md (the 9 sections).
- `references/interview.md` — the greenfield question flow.
- `references/example.md` — a full worked input→output sample for a polyglot project (self-contained; needs no external repos). Skim it for style before generating.
- `assets/*.template` — the file skeletons to fill and write into the target repo.
- `assets/permissions/` — the reference `ask` list for Claude Code and the reference pi file (Step 7).

is plain JSON, which allows no comments, so it carries no stamp.

## [api/proxy.js](api/proxy.js)

The proxy takes `?url=…`, fetches that address, and returns the body. It is the only server-side code in the project. I read it line by line and checked the main risks against Vercel's documentation. I haven't changed anything.

### 1. Response size (the one that may be breaking your site)

- **Limit:** Vercel's documentation says a function's response body can be at most 4.5 MB ([limits page](https://vercel.com/docs/functions/limitations)). Larger responses fail with an error.
- **Why the proxy hits it:** it loads the whole upstream response into memory and sends it in one piece ([lines 48–49, 82](api/proxy.js#L48-L49)).
- **Sample sizes:** the unpacked EPG in `tmp/` is 146 MB. I compressed it with gzip and got 17.4 MB. That is my estimate, and your provider's real `.gz` may differ somewhat. The cinema catalogue sample is 77 MB as plain text.
- **What the docs say about fixing it:** the Vercel docs say streaming a response lets a function return large data without hitting the limit. I haven't verified the exact code for a plain Node function, so I'd check that before proposing a change.

**Question for you:** does the EPG load on the deployed site, or only on localhost, where the app skips the proxy? If it works in production, one of my assumptions is wrong, for example your real file is smaller than my samples.

### 2. Anyone can use it as a free go-between

The only checks are that the address parses and starts with `http://` or `https://` ([lines 21, 27](api/proxy.js#L21)). Anyone who finds your site can send traffic through it at your cost, and redirects are followed without another check.

The obvious fix, a list of allowed hosts, conflicts with the app: users type in their own provider address. Your provider also uses port 8080, so blocking ports would break it too. More realistic limits are a size cap, a time limit, and blocking loopback and private-network addresses.

### 3. Possible script injection through XML responses (I haven't tested this)

- **Cause:** the allowed list includes `application/xml` and `text/xml` ([lines 60–61](api/proxy.js#L60-L61)).
- **Attack:** browsers can run scripts in XML pages that use the XHTML format. Someone could craft a proxy link to their own XML file and get you or another user to open it. The script would run on your site's origin and could read what the app saves in the browser (your EPG and cinema addresses, which may hold account codes, and ratings).
- **Fix:** one extra header on proxy responses, such as `Content-Security-Policy: sandbox`, would likely stop it. The app only calls the proxy through `fetch`, so it wouldn't be affected.

### 4. Smaller points

- **Logging:** line 32 writes the full address to Vercel's logs, which may include an account code.
- **Error message:** line 88 sends the raw error text back to whoever called the proxy.
- **No time limit:** there is no timeout on the upstream request. Vercel's default maximum is 300 seconds, so a slow server could hold the function for up to 5 minutes.
- **Scheme check:** the check is a case-sensitive string compare. It rejects `HTTP://`, which is harmless but not how it should be done.
